# v2.10 — Reconciling a third wave ("Phase 2-5 UI Bridge + Security Hardening")

## What happened

While the v2.9 Batch 1 reconciliation (`docs/v2.9-batch1-reconciliation.md`)
was itself landing on `main`, a third independent session pushed further
work directly to `main`, in two commits: a "Phase 2" frontend-integration
commit (`routers/ui_bridge.py`, `frontend/js/api-client.js`,
`frontend/js/integration-loader.js`) and a "Phase 3-5" commit titled
*"Integration testing, deployment, security hardening (100% production
ready)"* (rate limiting, input validation, security headers, OpenAPI docs,
Kubernetes manifests, a Docker production image, and a 50+ test integration
suite).

This session was never aware of any of the v2.6–v2.9 work — its own diff
against this branch showed it *deleting* `dependencies.py`,
`payloads/script_catalog.py`, and the `iam`/`vault`/`awareness`/`darkweb`/
`cheatsheet`/`response` routers, along with every doc and test this
reconciliation had already produced. Git's 3-way merge correctly
determined this was a false alarm — that session's own history never had
those files to begin with (it forked before any of this branch's work
existed), so nothing was actually deleted by the merge; every one of those
files survived intact. Only `backend/app.py` had a real 4-block content
conflict (import order, an `add_security_middleware` wiring line, the
`db = get_db_manager()` singleton line, and the `/api/telemetry/stream`
SSE endpoint's signature).

The `git merge` result showed **only** `app.py` conflicting. But
"survived the automated merge" and "actually works" are different claims,
as this reconciliation has now confirmed twice — so the same rule applied
again: run it for real, against a live app instance and (for the pieces
that specifically claimed "production ready" and shipped a 50+ test
integration suite) a live HTTP server, not just the merge tool's silence.

## `db = DuckDBManager()` vs. `db = get_db_manager()`, and one dropped fix

The `app.py` conflict's third block replaced this branch's
`db = get_db_manager()` (the process-wide singleton established in v2.6
specifically to avoid redundant DB connections) with the incoming
`db = DuckDBManager()` (a second, separate connection). Kept this branch's
singleton. The fourth block dropped the `request: Request` parameter from
`telemetry_stream()` -- silently reverting a real, previously-fixed
resource leak: without it, `request.is_disconnected()` can't be checked
inside the SSE generator, so a client that closes its tab or navigates
away leaves an orphaned generator (and its 3-second DB-poll loop) running
forever. Kept this branch's signature and the disconnect check.

## Six more real bugs, all reproduced before being fixed

### 1. `config.py`/`middleware.py` collide with the new `config/`/`middleware/` packages

The incoming commit added `backend/config/openapi_config.py` and
`backend/middleware/security_hardening.py`, expecting `config` and
`middleware` to be packages -- but `backend/config.py` and
`backend/middleware.py` (plain modules, pre-existing) were left in place
right next to the new directories, and neither new directory got an
`__init__.py`. Reproduced live: `ModuleNotFoundError: No module named
'config.openapi_config'; 'config' is not a package` (same for
`middleware`). Fixed by converting both into real packages
(`config.py` → `config/__init__.py`, `middleware.py` →
`middleware/__init__.py`) so both the existing `from config import
get_config` / `from middleware import TimingAndSecurityMiddleware` and the
new `from config.openapi_config import ...` / `from
middleware.security_hardening import ...` resolve correctly.

### 2. `routers/ui_bridge.py`: a silent, three-way path collision

`ui_bridge.py` defined `GET /api/fabric/status`, `GET /api/scripts/catalog`,
`GET/POST /api/resonance/policies`, and `GET /api/resonance/audit` --
paths already owned by `routers/fabric.py`, `routers/scripts.py`, and
`routers/resonance.py`, registered earlier in `app.py`. FastAPI/Starlette
resolves overlapping exact-path routes by registration order, so these
four `ui_bridge.py` endpoints were 100% unreachable dead code -- except
this branch's own `integration.js` and the new
`frontend/js/api-client.js` both call some of the same paths expecting
**different response shapes from different backend implementations**
(e.g. `fabric.py`'s `/status` returns `security_agents`' native
`FabricEngine.status()` shape; `ui_bridge.py`'s fabric endpoint returns a
flattened, dashboard-specific shape). Reordering router registration to
"fix" the dead code would have silently broken whichever frontend lost
instead. Fixed by renaming the four colliding `ui_bridge.py` routes under
a `/dashboard/` prefix (matching its own convention for its other 6
routes) and updating `frontend/js/api-client.js`'s 5 call sites to match
-- both frontends now reach their own real, distinct endpoint, verified
returning `200` with the expected distinct shapes.

### 3. `GET /api/dashboard/matrix` queried a nonexistent column

Selected `findings.cvss_score`, which doesn't exist in the real `findings`
schema (`id, pentest_id, severity, title, description, attack_technique,
remediation, created_at` -- no CVSS field) -- a live
`duckdb.duckdb.BinderException` on every call. Fixed by deriving a `score`
from the real `severity` column instead (`CRITICAL`→1.0, `HIGH`→0.75,
`MEDIUM`→0.5, `LOW`→0.25).

### 4. `InputValidator`: a global false-positive generator

`middleware/security_hardening.py`'s `InputValidationMiddleware` runs on
**every** query param, path param, and JSON body field across the entire
app (`add_security_middleware(app)` wires it globally). Its `sql_injection`
pattern blocklisted the bare word `SELECT|INSERT|UPDATE|DELETE|DROP|
CREATE|ALTER|EXEC|EXECUTE` (`\b`-delimited, so matching as a *substring*
of any longer identifier separated by non-word characters) plus any lone
`'`, `"`, `;`, `--`, `/*`, or `*/`; its `command_injection` pattern
blocklisted any lone `; & | \` $ ( ) { } [ ] < >`. Reproduced live: a
perfectly ordinary target string, `"payload-exec-123"`, was rejected with
a 400 as `"sql_injection"` because it contains "exec" as a
word-boundary-delimited substring. The same patterns would reject any
field containing an apostrophe (`"don't"`), a MITRE technique ID with a
sub-technique in parens (`"T1059(001)"`), or any of dozens of common
English/technical words as substrings -- applied to every field of every
request. This app already uses parameterized queries everywhere (no raw
SQL string interpolation), so this middleware is defense-in-depth, not
the actual injection defense; it should not be blocking legitimate
traffic to provide that marginal extra layer. Retuned to match actual
attack *shapes* (`UNION SELECT`, stacked queries `; DROP TABLE ...`,
classic tautologies `OR 1=1`, comment-truncation `--`/`/* */`, real shell
metacharacter sequences like `` `cmd` `` or `$(cmd)`, and traversal
sequences repeated 2+ times or targeting `/etc`, `/windows`, `system32`)
instead of individual characters or dictionary words. Verified: the
benign strings above now pass; `"1 UNION SELECT username, password FROM
users"`, `"'; DROP TABLE users; --"`, and `"admin' OR '1'='1"` are still
rejected.

### 5. The `action` field whitelist didn't match the real allowed values

`InputValidator.WHITELISTS["action"]` allowed `scan|isolate|quarantine|
block|monitor`, but `routers/ui_bridge.py`'s own `DeviceActionRequest.action`
field documents the real allowed values as `scan, isolate, reset_pass,
quarantine, release` -- two of the five real actions (`reset_pass`,
`release`) would have been rejected by the whitelist on every call to
`POST /api/dashboard/fleet/{id}/action`, while two whitelisted values
(`block`, `monitor`) aren't valid inputs at all. Fixed to match the real
model.

### 6. CRITICAL: concurrent DB access segfaults the whole process

`database.py`'s `DuckDBManager` wraps one `duckdb.Connection`, shared
process-wide via the `get_db_manager()` singleton. A direct, minimal
reproduction --10 threads, each looping `conn.execute("SELECT ...")`
against that one shared connection -- reliably crashes the Python
interpreter itself (`SIGSEGV`, process exit code 139), not a catchable
exception. FastAPI's `run_in_threadpool()`, used by essentially every
router in this codebase for DB calls, genuinely dispatches different
requests' work to different worker threads whenever two requests overlap
in time -- which is completely ordinary under real concurrent usage (two
browser tabs open, one tab plus a live SSE telemetry stream, two people
using the demo at once), not a synthetic stress-test edge case. This was
caught for real: the incoming "Phase 3" integration suite's
`test_sse_concurrent_listeners` test, run against a live `uvicorn`
instance, crashed the server outright -- every subsequent HTTP request in
that test run failed with `ConnectError` because there was no process left
to connect to.

Fixed with a `_LockedConnection` wrapper (`database.py`) around the shared
connection:
- `execute()` acquires a lock, runs the real `execute()` + `fetchall()`,
  and captures `.description` -- all still inside the lock -- then returns
  a `_MaterializedResult` built from that already-fetched data. This
  covers the chained pattern used almost everywhere in this codebase
  (`conn.execute(sql).fetchall()` / `.fetchone()`) with zero call-site
  changes.
- A second pattern also appears throughout (`conn.execute(sql)` on one
  line, `conn.description` read separately on a later line, ~39 call
  sites in `database.py` alone): that `.description` access is served
  from `threading.local()` storage, so each thread's own last `execute()`
  populates only that thread's slot -- a standalone read always reflects
  that *same* thread's own last query, with no possible cross-request
  interference, because one HTTP request's DB work runs synchronously on
  one threadpool worker thread from start to finish.

Verified: the same 10-thread repro (and a 15-thread/1500-query variant
through the real `DuckDBManager`) completes with zero errors and correct
results after the fix. Re-ran the "Phase 3" integration suite against a
live server: it no longer crashes the process (24+ tests now actually
execute and pass, up from 16 before this fix, with the remainder either
correctly rejected by the new rate limiter under rapid test traffic or
failing for an unrelated, pre-existing reason -- a second process can't
open an exclusively-locked DuckDB file that a live server already has
open, a limitation of the test file's own design, not an application bug).

### 7. `GET /` never actually served the UI (pre-dates all three waves)

`app.py`'s `_FRONTEND` default was `<repo_root>/frontend`, but `index.html`
and `integration.js` (the real, fully-built operator UI referenced
throughout this entire multi-session build) have always lived at the repo
root directly, not in a `frontend/` subdirectory. This bug predates the
three reconciliation waves -- it was already present and already logging
`FRONTEND_DIR missing ... UI will not be served` the very first time this
reconciliation booted the app, before any of the merges in this document.
Confirmed live: `GET /` returned `200 application/json` (the "UI not
bundled" fallback), not the UI, and `GET /integration.js` 404'd. The
Phase-2 wave's two new JS files (`frontend/js/api-client.js`,
`frontend/js/integration-loader.js`) had been placed to match this same
wrong default, rather than next to `index.html` where its own
`<script src="./js/...">` tags actually look for them.

Fixed by pointing `_FRONTEND`'s default at the repo root, and moving the
two JS files to `js/api-client.js` / `js/integration-loader.js`
(repo-root-relative, matching `index.html`'s existing relative paths).

That fix introduced a second, more serious issue on its own: mounting the
entire repo root as `StaticFiles` serves everything under it over HTTP as
a side effect. Confirmed live: `GET /backend/database.py` and
`GET /.git/config` both returned `200` with the real file contents --
publishing the full backend source tree and git internals (and, had one
existed, any local `.env` a developer keeps in `backend/`, which is
gitignored but StaticFiles doesn't know that). `index.html` only
references three local assets (`./js/api-client.js`,
`./js/integration-loader.js`, `./integration.js` -- everything else it
loads is from a CDN), so the fix mounts only the `js/` subdirectory plus
one explicit `GET /integration.js` route, instead of the whole tree.
Verified: the UI and its two JS assets still return `200`;
`/backend/database.py`, `/backend/config/__init__.py`, `/.git/config`,
and `/docs/*.md` all now correctly 404.

## What was also cleaned up

- Removed unused imports across `app.py`, `config/__init__.py`,
  `config/openapi_config.py`, `middleware/security_hardening.py`, and
  `models.py` (pyflakes clean on all of them).
- `tests/integration/test_phase3_complete.py` is a **live-server**
  integration suite (`httpx.Client()`/`AsyncClient(base_url=BASE_URL)`
  against `http://localhost:8000`), architecturally different from the
  rest of `tests/`, which drives the app in-process via `ASGITransport`
  and needs no running server. Fixed a genuine syntax error in it
  (`await` used inside a non-`async def`) and added a
  `pytest.mark.skipif` guard so it skips cleanly when no live server is
  reachable (a normal `pytest tests/` run) instead of failing all 32 of
  its tests with `ConnectError`, while still running for real against an
  actually-started server.
