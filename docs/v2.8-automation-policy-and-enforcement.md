# JAKAL v2.8 — Resonance Wave Automation Policy + Real Containment Enforcement

This closes the two gaps called out explicitly at the end of v2.7:
Resonance Wave Automation had no write control, and host isolation was a
staged decision with no enforcement path. Both are now real — grounded in
research on how production SOAR platforms actually solve the same
problem, not invented from scratch.

## Why `resonance_policy` is a NEW table, not a patch to `global_security_settings`

`global_security_settings` (v2.4) is documented as deliberately
**derived** — computed fresh from the real `operators`, `encryption_keys`,
and `pqc_audit_log` tables on every snapshot, specifically so it can never
become a second, driftable source of truth for security posture (the same
principle `horizon_trust_fabric` follows in v2.5). Adding a naive
`POST /resonance/settings` that let someone PATCH that snapshot directly
would have reintroduced exactly the anti-pattern this codebase has
avoided twice already.

`resonance_policy` (v2.8) is a genuinely different thing: a small set of
independently-meaningful automation knobs, each one **read by a real
enforcement point** rather than being a decorative flag:

| Policy key | Type | Read by |
|---|---|---|
| `response_auto_stage_threshold` | number | `POST /api/response/triage` — org-wide default (per-call `auto_stage_threshold` still overrides it) |
| `trade_secret_isolation_enforced` | bool | `POST /api/vault/items` — rejects an empty `allowed_roles` list when on |
| `auto_approve_low_risk_actions` | bool | `POST /api/cheatsheet/scripts/{id}/stage` — LOW-risk scripts only; MEDIUM/HIGH/CRITICAL always need a human regardless |
| `sandbox_max_lifetime_hours` | number | `GET /api/resonance/policy/stale-sandboxes` — informational, nothing auto-destroys a sandbox |

Every change is RBAC-gated (`response:manage`), written to `audit_log`,
and PQC-signed (ML-DSA-65) the same way every other security-relevant
decision in this platform already is — config management with change
control, matching NIST SP 800-53 CM-3 (Configuration Change Control).

## Real containment enforcement (`security_agents/edr_connector.py`)

Two connectors, chosen honestly by what this platform actually controls:

**1. `DockerSandboxIsolationConnector` — real, for infrastructure this
platform owns.** A JAKAL-provisioned sandbox container
(`security_agents/vm_orchestrator.py`) gets genuinely disconnected from
every Docker network it's attached to, via the same `docker` SDK client
VMOrchestrator already uses. This is real MITRE D3FEND D3-NI (Network
Isolation), not a simulation — proven in
`tests/test_v28_policy_enforcement.py` by actually creating a Docker
network and container, isolating it, and asserting the network list is
empty afterward. The ownership check (`jakal.sandbox` label) is the same
one `VMOrchestrator.exec_in_sandbox` already enforces, applied here too.

**2. `WebhookEnforcementConnector` — the real integration point for
infrastructure this platform does NOT own.** Researched against how
production SOAR tools actually bridge to a real EDR: Cortex XSOAR's
CrowdStrike Falcon isolation playbook and Splunk SOAR's CrowdStrike
connector both call the vendor's own device-isolation API using the
customer's own API credentials — no third party can call that API
without them. [Cortex XSOAR: CrowdStrike Falcon — Isolate Endpoint](https://xsoar.pan.dev/docs/reference/playbooks/crowdstrike-falcon---isolate-endpoint), [Hexastrike: Automating CrowdStrike Network Containment](https://hexastrike.com/resources/blog/dfir/automating-crowdstrike-network-containment/), [SentinelOne: What is SOAR?](https://www.sentinelone.com/cybersecurity-101/data-and-ai/what-is-security-orchestration-automation-and-response-soar/)
So the connector fires a **signed webhook** — `EDR_WEBHOOK_URL` — that an
operator points at whatever bridges to their real EDR/firewall (a
Shuffle workflow, their own Falcon/Singularity API wrapper, a firewall's
webhook-triggered ACL update). Every production webhook-security guide
agrees on the shape: sign the raw body with HMAC-SHA256, include a
timestamp and nonce for replay protection, verify with a constant-time
comparison. [Hooklistener: Webhook Security Guide](https://www.hooklistener.com/learn/webhook-security-fundamentals), [Hook0: Verify webhook HMAC signatures](https://documentation.hook0.com/tutorials/webhook-authentication)
`verify_webhook_signature()` in `edr_connector.py` is the reference
receiver-side implementation — copy it into whatever service
`EDR_WEBHOOK_URL` points at.

Without `EDR_WEBHOOK_URL`/`EDR_WEBHOOK_SECRET` configured, enforcement
against a non-sandbox target reports `enforcement_not_configured`
honestly — it never pretends to have acted.

## The enforcement flow

```
POST /api/response/isolate-host          -> always staged (approval_requests row)
POST /api/approval/{id}/approve          -> human decision (existing endpoint, unchanged)
POST /api/response/actions/{id}/enforce  -> NEW. 403s if not yet approved. Otherwise:
    target is a live JAKAL sandbox?  -> real Docker network disconnect
    target is external?              -> signed webhook to EDR_WEBHOOK_URL (or "not configured")
```

`quarantine-host` (`POST /api/response/quarantine` with `target_type:
"host"`) follows the identical staged → approve → enforce path.
`quarantine-artifact` stays immediate/data-layer, unchanged from v2.7 —
only the two actions that claim to touch real infrastructure needed this.

## Testing

11 new tests in `tests/test_v28_policy_enforcement.py`, two of which are
real integration tests rather than mocks:

- **Docker isolation**: builds a ~2MB `FROM scratch` test image locally
  from the OS's own `busybox-static` package (Docker Hub's CDN is not
  reachable from this environment's egress policy; Ubuntu's package
  archive is — so the test image is built with zero external image
  pulls), creates a real bridge network + labeled container, calls the
  connector, and asserts the container's network list is empty
  afterward. A second test proves the ownership check rejects a
  non-`jakal.sandbox`-labeled container. Both `skipif` cleanly when no
  Docker daemon is reachable.
- **Webhook delivery**: a real local `http.server` thread receives the
  connector's actual HTTP POST and the test verifies the received
  signature against `verify_webhook_signature()` — proving sender and
  the documented receiver implementation actually agree, plus that a
  wrong secret correctly fails verification.
- **End-to-end**: the full `isolate-host` → `approve` → `enforce` API
  path, asserting the `remediation_actions` row reflects the real
  outcome — this test caught a genuine bug (see below).

### Bug found and fixed while writing these tests

`enforce_action`'s status update matched on `action_id`, but the
`remediation_actions` row `isolate_host`/`quarantine` create has its own
independently-generated `action_id`, linked to the approval only via the
`approval_request_id` column — the update silently matched zero rows, so
a real, successful enforcement never updated its own status past
`staged`. Fixed with a new `update_remediation_action_status_by_approval()`
method keyed correctly; caught by the end-to-end test asserting the row's
status after a real enforce call, not just the API response.

Full suite: **107 passed**, verified on **10 consecutive full runs**
(4 before this bugfix reproducing it consistently, 6 after confirming the
fix and overall determinism) — including the real Docker container/network
tests each time, with a post-run check confirming zero leaked containers
or networks.
