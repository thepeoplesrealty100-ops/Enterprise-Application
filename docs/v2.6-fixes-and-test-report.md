# v2.6 Troubleshooting Pass — Bugs Found & Fixed

Full test-suite run before any change in this session: **53 passed, 16
failed, 6 errors** (`backend/tests/`, `python -m pytest tests/ -q`).
Confirmed via `git stash` that every one of those 22 failures/errors was
already present on the branch before this session touched anything — none
were introduced by the v2.6 work; they're independent pre-existing bugs
this pass also happened to fix along the way.

After fixes: **85 passed, 0 failed, 0 errors** (74 from the pre-existing
suites + 11 new tests added for v2.6 — see
`backend/tests/test_v26_settings_security.py`), and a second consecutive
run against the same persisted dev database repeats the same 85/0/0
result. `backend-v3/`'s independent test suite: **53 passed, 0 failed**
(unchanged — already green, not touched).

## Root causes fixed

1. **`anthropic==0.25.0` pinned without pinning its `httpx` dependency.**
   A clean `pip install -r requirements.txt` today pulls current `httpx`
   (0.28+), which removed the `proxies=` kwarg that `anthropic==0.25.0`'s
   client passes internally — `import app` crashed on
   `TypeError: Client.__init__() got an unexpected keyword argument
   'proxies'` before the backend could serve a single request, on every
   fresh install. Fixed by bumping to `anthropic>=1.2.0,<2.0.0` (the
   `Anthropic(api_key=...)` / `.messages.create(...)` call sites in
   `llm_orchestrator.py` are stable across that range).

2. **`AgentOrchestrator.initialize_llm()` had no failure isolation.**
   Since it's instantiated at *module import time* in `app.py`, any
   failure constructing the Claude client (missing API key, a stubbed/
   incompatible `anthropic` module — exactly what
   `tests/test_suite.py` does via
   `sys.modules.setdefault("anthropic", types.ModuleType("anthropic"))`
   to avoid needing a real key in CI) took down the *entire* API process,
   not just LLM-backed endpoints — including `/health`, which ops tooling
   uses to know the process is even alive. Fixed: client construction is
   now wrapped in try/except; on failure `self.client` stays `None`,
   logged as a warning, and only `_call_claude()` (correctly) fails for
   that one call.

3. **`UPDATE ... RETURNING <pk-column>` throws a spurious
   `ConstraintException` on the pinned `duckdb==0.10.0`**, specifically
   against tables whose primary key is `INTEGER PRIMARY KEY DEFAULT
   nextval(<sequence>)`. Reproduced 100% of the time, not a flake — this
   DuckDB version appears to re-evaluate the PK's `DEFAULT` expression
   during `RETURNING` row materialization instead of echoing the already-
   assigned value, colliding with the row's own id. This broke:
   - `rotate_encryption_key` / `revoke_encryption_key` (Key Management)
   - `decide_approval_request` / `expire_stale_approval_requests` (the
     entire Human Approval Gate approve/deny path)
   - `link_unified_event_approval` (Ares cross-pillar event linking)
   - `expire_threat_intel` (not covered by an existing test, but the same
     latent bug — fixed proactively)

   Fixed by dropping `RETURNING` in favor of a `SELECT`-existence-check
   (or `SELECT COUNT(*)`) before the `UPDATE`, matching the pattern
   already used successfully elsewhere in `database.py` (and the pattern
   the new v2.6 methods use throughout).

4. **12 of 14 router modules each called `DuckDBManager()` directly at
   import time** — 12+ separate connections to the same on-disk file and
   12+ redundant re-runs of the ~40-statement `initialize_schema()` on
   every process start. Fixed with a process-wide singleton
   (`database.get_db_manager()`); every router and `tools/authorization.py`
   now share one instance. `app.py` and all 12 routers updated.

5. **Two stale tests referencing removed/renamed contracts:**
   - `test_scan_repository_lifecycle` imported `from repository import
     ScanRepository` — no such module exists anywhere in the codebase
     (confirmed by repo-wide grep); pentest persistence goes straight
     through `DuckDBManager.insert_pentest()` now, no repository layer was
     ever built. Removed rather than resurrecting an unused module.
   - `test_pentest_start_missing_target` / `test_pentest_start_valid`
     POSTed to `/api/pentest/scan` (a path that has never existed in
     `routers/pentest.py` — only `POST /pentest/run` is defined) and
     asserted an async-job-queue contract (`status: "queued"`) that the
     current, deliberately-synchronous pipeline doesn't have. Rewritten
     to hit the real endpoint and assert the real
     `PentestResponse` contract; also had to seed an authorization scope
     for the test target, since the previous version only "passed" by
     accident when a prior test in the same run happened to leave a
     matching scope in the shared on-disk DB.

## `backend/app.py` — security & correctness fixes (router review)

- `schemas.py` already defined proper Pydantic request models
  (`ScopeAddRequest`, `VMExecRequest`, `PlaybookExecuteRequest`, etc.) that
  were never imported into `app.py` — every one of those endpoints took a
  raw `dict` instead, so a malformed request raised an unhandled
  `KeyError` → bare 500 instead of a clean 422. Wired the existing models
  in; no new validation logic needed, it already existed and was unused.
- `GET /api/telemetry/stream` (SSE) never checked for client disconnect —
  every browser tab close or navigation left its `while True: asyncio.sleep(3)`
  generator (and DB poll) running forever. Fixed with
  `await request.is_disconnected()`.
- `POST /api/vm/sandboxes/{name}/exec` — arbitrary command execution
  inside a sandbox container — had **zero** access control beyond an
  unvalidated free-text `command` string. Now requires the `vm:exec`
  permission (see `dependencies.py`) and rejects commands over 4000 chars.
  `vm:manage` (create/destroy) and `scope:manage` (authorization scope/
  insurance) endpoints gated the same way.
- Blocking, synchronous DuckDB calls inside `async def` handlers (agent
  logs, telemetry polling, VM operations, compliance reports, EDR
  playbooks) now run via `fastapi.concurrency.run_in_threadpool` instead
  of blocking the single asyncio event loop for every concurrent request.
- `GET /api/agent/logs` had an unbounded `limit` query param; clamped to
  `[1, 500]`.

## Known pre-existing issue *not* fixed in this pass (documented, not silently left)

`backend-v3/README.md` independently documents the same class of findings
this session found in `backend/` (its own GAP-01 = no auth, GAP-03 = PK
collision, GAP-04 = boot crash on default config) as a "clean-room
rebuild" — confirming these are known, previously-identified architectural
issues, not new discoveries this pass invented. `backend-v3` is scoped as
a *reference implementation* for a subset of modules (identity, PQC,
approval gate, Ares, Canvas, quantum queue), not a full replacement for
`backend/`; migrating the rest of `backend/`'s ~32 tables onto that
pattern (async SQLAlchemy, Postgres-capable, per-test isolated DB) is a
larger, separate effort than this session's scope.
