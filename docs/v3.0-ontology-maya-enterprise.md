# v3.0 — Ontology Engine + Maya-Vigesimal Calendar 2FA

## What this adds

Five additive DuckDB tables (`database.py`), a Palantir Foundry-style
Object/Link digital twin service (`services/ontology_engine.py`), a
calendar-coordinate second factor interlocked with the existing v2.3
Human Approval Gate (`security_agents/exploit_agent.py`), two new routers
(`/api/v3/ontology/*`, `/api/v3/auth/maya/*`), and a frontend modal
(`integration.js`). Nothing existing changed shape: the schema is purely
additive, the approval gate's own approve/deny/execute flow is untouched,
and every pre-existing router, table, and test keeps working exactly as
before.

- **Ontology Engine**: `ontological_object_nodes` (free-text object types
  — "Asset", "Finding", "ScanResult", "RemediationAction" — each carrying
  a JSON attribute bag and a confidence score) + `lattice_edge_telemetry`
  (directed, typed edges — "AFFECTS", "ISOLATED", "QUARANTINED",
  "DISCOVERED_BY" — between them). `OntologyEngine.query_subgraph()` does
  a breadth-first traversal for attack-path/blast-radius style queries.
- **Maya-Vigesimal 2FA**: every HIGH/CRITICAL payload
  `ExploitAgent.stage_payloads()` stages also gets a Tzolkin/Haab
  "Calendar Round" coordinate pair and a short derived token
  (`maya_vigesimal_auth_sessions`), which the operator must echo back via
  `POST /api/v3/auth/maya/verify` before deciding the payload's actual
  approval (`POST /api/approval/{id}/approve`) — a genuine second factor,
  not a replacement for the approval gate.
- **Resonance policy enforcements**: `resonance_policy_enforcements`, a
  named, `module_target`-scoped policy table any module can register
  against — distinct from `automation_settings` (a small set of global
  on/off knobs) and Batch 1's `resonance_policy` (isolation-specific
  enforcement policies); see `database.py`'s v3.0 schema comment for how
  all three coexist.
- **Q'AIP inference registry**: `q_aip_inference_registry`, a PQC-signed
  audit trail of quantum-circuit executions, optionally linked to an
  ontology node.

## Real bugs found in the original spec and fixed

This was handed to me as literal, ready-to-paste code. Testing every
piece against the actual pinned `duckdb==0.10.0` and the actual
codebase — rather than trusting the snippets — surfaced six real, blocking
problems, all reproduced empirically before being fixed:

1. **Five declared-but-unused sequences.** The spec's schema created
   `seq_ontological_nodes`, `seq_lattice_telemetry`, `seq_maya_sessions`,
   `seq_resonance_policy`, and `seq_qaip_inference` via a loop, but every
   one of the five new tables' primary keys is a UUID string
   (`str(uuid.uuid4())`), not a sequence-backed integer — none of them
   are ever referenced by a `DEFAULT nextval(...)`. Dropped as dead code.
   (`seq_resonance_policy` would also have been a confusing near-name-
   collision with Batch 1's already-existing `seq_resonance_policy`,
   despite backing an unrelated table.)
2. **`ON DELETE CASCADE`/`SET NULL` on FOREIGN KEY REFERENCES**: DuckDB's
   parser rejects both outright (`FOREIGN KEY constraints cannot use
   CASCADE, SET NULL or SET DEFAULT`), confirmed by reproduction — the
   schema would never have created successfully as written.
3. **Creating a secondary index before a FOREIGN-KEY-referencing table
   exists**: raises `Cannot alter entry ... because there are entries
   that depend on it` in this DuckDB version — confirmed by reproduction.
   Fixed by creating all tables before any index (still not sufficient on
   its own — see #4).
4. **FOREIGN KEY REFERENCES blocks UPDATE on *any* column of a referenced
   row**, not just deletes or the key column itself — confirmed directly
   against this schema: `update_node_confidence()` on a node that had
   ever been linked into the graph (the normal case) failed with
   `Violates foreign key constraint`. This alone made the whole
   REFERENCES approach untenable, so source_node/target_node/
   related_node_id are application-level foreign keys instead — checked
   for existence in Python before insert, exactly matching this schema's
   own pre-existing, explicitly-stated convention (`role_permissions`'
   comment: "not FKs; DuckDB has no enforced FK constraints, kept
   consistent with the rest of this schema").
5. **CRITICAL: any secondary index at all breaks UPDATE with a spurious
   primary-key violation.** Isolated to a 6-line minimal repro: a table
   with one `CREATE INDEX` (on any column) makes every subsequent
   `UPDATE` against it fail with `Constraint Error: Duplicate key ...
   violates primary key constraint` — regardless of which column is
   indexed or which column the UPDATE touches. This would have broken
   `update_node_confidence()` and every status transition in
   `consume_maya_session()`. Fixed by giving `ontological_object_nodes`
   and `maya_vigesimal_auth_sessions` (the two tables anything UPDATEs)
   no secondary indexes at all — only their implicit PRIMARY KEY index,
   which is safe. The other three v3.0 tables are append-only, so their
   indexes are unaffected and kept.
6. **`cursor.rowcount` is always `-1`** in this DuckDB version for UPDATE
   statements (confirmed empirically) — the spec's
   `update_node_confidence()` used `result.rowcount > 0` to report
   success, which would always evaluate false even on a real, successful
   update. Fixed with the SELECT-then-UPDATE pattern already established
   elsewhere in `database.py` for this exact class of DuckDB limitation.
7. **The spec's own lifecycle test was unsatisfiable by its own
   implementation.** `consume_maya_session()` marked a session
   permanently `'denied'` on any wrong-token attempt — but the spec's own
   `test_maya_session_lifecycle` submits a wrong token and then the
   correct one against the *same* session, expecting the second call to
   succeed. A permanent denial on first mismatch makes that impossible.
   Fixed so a wrong token returns an error without consuming the session,
   allowing retry until expiry — matching the lifecycle the spec's own
   test actually exercises, and a better UX besides (a typo doesn't burn
   the whole 5-minute window).

## Frontend

`showMayaChallengeModal()` is hooked generically into `integration.js`'s
shared `api()` wrapper: any response carrying a `maya_challenge` (a
top-level key, or nested in a `payloads[]` array) triggers the modal
automatically, regardless of which endpoint staged the payload
(`/api/approval/stage`, `/api/canvas/*`, or any future one) — since
`ExploitAgent.stage_payloads()` is the single choke point all of them
share. The spec assumed an existing "HIGH/CRITICAL staging response
handler" to extend; no such handler existed in this codebase (staging
wasn't wired to any UI trigger yet), so this generic hook was the correct
integration point instead of inventing a narrower one. A "Stage HIGH-risk
demo payload" button was added to the Approval tab so the modal is
actually reachable from the browser.

## Addendum: Phase 0 — the interlock fix

The initial build above shipped Maya as a **parallel confirmation step**,
not a real interlock: `approve_payload()`/`reject_payload()` never
actually checked a linked session's status, and the modal + challenge
response leaked the raw Tzolkin/Haab coordinates and an unmasked token.
Verified and fixed:

- `maya_vigesimal_auth_sessions` gained `display_issued_at`/
  `display_expires_at` (`TIMESTAMPTZ`, populated in `create_maya_session`).
- `_maya_vigesimal_challenge()` now returns only `session_id`,
  `challenge_token`, `display_issued_at`, `display_expires_at`, `status`
  — the calendar coordinates and raw expiry stay internal to the DB row.
- New `DuckDBManager.get_maya_session_by_payload_id()` lookup;
  `ExploitAgent._maya_interlock_gate()` refuses an approve/reject decision
  unless the linked session's status is `'consumed'`, and threads
  `maya_session_id` into the PQC-signed audit entry for that decision.
  A payload with no Maya session at all (LOW/MEDIUM risk) is unaffected —
  the gate only ever tightens a decision that was already challenged.
- The frontend modal shows only the friendly issued/expires dates by
  default, with the raw token masked behind a Show/Hide toggle.

Full suite: 145 passed, 41 skipped, 0 failed after this fix (was 138).

## Addendum: Phase 1 — formalizing the step-up authenticator

Maya-Vigesimal is explicitly **not login MFA**. It is an internal
high-assurance step-up authenticator, triggered only for HIGH/CRITICAL
staged payloads, layered on top of the (unmodified) Human Approval Gate —
see `security_agents/exploit_agent.py`'s Maya-Vigesimal module comment for
the full design rationale, including the Zero Trust ("never trust, always
verify") framing and why a login-MFA design was rejected.

Two gaps closed:

- **Consumption is now a first-class audit event.** Creation was already
  PQC-signed (`maya_challenge_created`); successful consumption was not.
  `ExploitAgent.consume_maya_challenge()` wraps
  `db.consume_maya_session()` and, only on a successful (`'consumed'`)
  result, writes a `maya_challenge_consumed` entry linking `session_id`
  and `payload_id` into the same ML-DSA-65-signed `pqc_audit_log` used by
  every other decision. A failed attempt (wrong token, expired, already
  consumed, not found) is never signed — there is nothing legitimate to
  attest to yet. `routers/maya_auth_router.py`'s `POST /verify` now calls
  this instead of the raw DB method.
- **`GET /session/{id}` no longer leaks internal calendar values by
  default.** It previously always returned `tzolkin_coordinate`/
  `haab_coordinate`/raw `expires_at` — inconsistent with the dual-mode
  design the challenge-creation response follows. It now returns only
  `display_issued_at`/`display_expires_at` by default, and reveals the
  Tzolkin/Haab coordinates + raw `expires_at` only with an explicit
  `?reveal_internal=true` query param — the "Show cryptographic details"
  auditor toggle, default hidden.

Full suite: 147 passed, 41 skipped, 0 failed after Phase 1 (2 new tests).
