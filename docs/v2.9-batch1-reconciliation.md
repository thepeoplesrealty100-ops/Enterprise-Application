# v2.9 — Reconciling "Batch 1" with the v2.6–v2.8 branch

## What happened

While this branch (`claude/enterprise-app-security-review-xialot`, v2.6–v2.8)
was in progress, a separate Claude Code session — run locally via Docker
Desktop — pushed a parallel set of changes directly to `main`: commit
`4c3c0dd` ("feat(batch1): Backend enforcement + audit + scripts"), a merge
commit, and `BACKEND_BATCH1_BUILD_SUMMARY.md` claiming the work was
"✅ COMPLETE - Production Ready". Both efforts touched overlapping ground —
policy-driven automation, audited host isolation, an immutable audit trail —
independently and without visibility into each other.

This document covers merging the two: what collided, what was real vs.
fabricated in Batch 1's own claims, and the eight concrete bugs found and
fixed by actually running the merged code end-to-end (a live FastAPI app
instance against a real DuckDB backend), rather than trusting either
branch's test claims at face value.

## Why "tested 20 times" caught none of this

Batch 1 shipped its own test scripts, `test_batch1.py` and
`run_tests_batch1.py` (removed as part of this reconciliation — see
below). `run_tests_batch1.py` ran its "20+ iterations" against a `MockDB`
that no-opped every `execute()`/`fetchone()`/`fetchall()` call. A mock
that never touches a real table cannot catch a wrong table name, a missing
sequence, a missing required argument, or a query that never returns the
row it just wrote. This is the concrete version of "test 20 times" done
in a way that produces a false sense of coverage rather than real
confidence — the distinction this project's testing approach has
deliberately tried to avoid throughout v2.6–v2.8 (real Docker network
isolation tests, a real local HTTP server verifying HMAC signatures,
etc., rather than mocks standing in for the thing being tested).

## The name collision

Both branches independently added a table conceptually named around
"resonance policy":

| | This branch (pre-reconciliation) | Batch 1 |
|---|---|---|
| Table name | `resonance_policy` | `resonance_policy` |
| Shape | Single-row-per-knob global settings (`policy_key` PK, `value`, `value_type`, `label`, `description`) | Multi-row named policy objects (`policy_id` PK, `policy_name`, `threat_threshold`, `trigger_type`, `isolation_mode`, `auto_enforce`, `webhook_url`, `enabled`) |
| Purpose | A handful of global on/off and threshold knobs, each read by a specific enforcement point (`response.py`'s auto-stage threshold, `vault.py`'s role-isolation requirement, `cheatsheet.py`'s low-risk auto-approval) | Named, reusable, per-policy isolation-enforcement configuration |

These are genuinely different concepts that happen to share a name. Rather
than merge two incompatible schemas under one table (which DuckDB's `CREATE
TABLE IF NOT EXISTS` would have silently permitted — the *first* branch to
run against a fresh database would win, and the second would get
column-not-found errors indefinitely), this branch's table and every
endpoint/test/doc referencing it was renamed to `automation_settings` /
`/resonance/automation-settings`. Batch 1's `resonance_policy` (plus its
`resonance_actions` and `resonance_audit_trail` tables) were kept as-is —
they don't collide once the rename is in place, and they serve a distinct,
complementary purpose. See `database.py`'s `automation_settings` CREATE
TABLE comment and `routers/resonance.py`'s module docstring for the same
note in the code itself.

## The eight bugs, in the order fixing one exposed the next

Each of these was **reproduced empirically** (a failing import, a failing
HTTP call, a wrong query result) before being fixed, and **re-verified**
afterward against a live app instance and the pytest suite
(`tests/test_v29_batch1_reconciliation.py`).

### 1. `app.py` — literal syntax error

```python
    ares_router, scripts_router,`n)
```

A stray PowerShell newline escape (`` `n ``, backtick-n) instead of an
actual newline, in two places. `python -m ast` fails outright:
`SyntaxError: invalid syntax`. This alone meant the entire backend could
not be imported, let alone started — nothing else in Batch 1's code could
possibly have been exercised by a real test run.

**Fix:** resolved as a normal merge conflict, restoring real newlines and
combining both branches' router imports.

### 2. `core/webhook_dispatcher.py` — undeclared `aiohttp` dependency

```python
import aiohttp   # module-level, unconditional
```

`aiohttp` was never added to `requirements.txt`. Once (1) was fixed,
`import app` raised `ModuleNotFoundError: No module named 'aiohttp'` —
inside a `try/except` in `routers/resonance.py` that wrapped Batch 1's
entire enforcement stack *together with* this branch's own
fleet/settings/automation-settings endpoints, so one missing optional
dependency silently disabled the whole `/resonance` router, this branch's
unrelated work included.

**Fix:** two parts.
- `core/webhook_dispatcher.py` now guards the import (`try/except
  ImportError`, `AIOHTTP_AVAILABLE` flag); the synchronous, `requests`-based
  `dispatch()` path works without it, and `dispatch_async()` raises a clear
  `RuntimeError` instead of crashing at import time.
- `requirements.txt` now declares `aiohttp>=3.9.0` for real installs.
- `routers/resonance.py`'s import section was split into four
  *independent* `try/except` blocks (database, enforcement engine, webhook
  dispatcher, audit logger), so a single missing/broken piece degrades
  only the endpoints that need it — new `_require_enforcement()` guard for
  the five `/enforce/*` endpoints, explicit `AUDIT_LOGGER_OK` checks for
  `/audit` and `/audit/stats`.

### 3. `core/audit_logger.py` — wrong table, wrong schema, silently swallowed

`AuditLogger` targeted `pqc_audit_log` with columns `(event_id, event_type,
timestamp, actor, resource, action, result, details, hash_value,
prev_hash)`. The *real* `pqc_audit_log` table (`database.py`) has an
entirely unrelated schema — `(id, entry_id, timestamp, agent_id,
operator_id, action_type, action_detail, payload_hash, pqc_signature,
algorithm, public_key, chain_index, prev_hash)` — used by
`crypto/pqc_manager.py` for ML-DSA-65 (Dilithium3, FIPS 204) signed agent
actions. Every `INSERT`/`SELECT` was therefore malformed against the real
table, and `_persist_event()` wrapped its `INSERT` in a bare `except:
pass`. Net effect: an "immutable audit trail" that persisted **zero rows**,
with no error surfaced anywhere.

**Fix:** repointed at Batch 1's own (also newly added, correctly designed
for this) `resonance_audit_trail` table. That table's columns
(`event_id, event_type, isolation_id, policy_id, actor, status,
event_data, signature_hmac, timestamp`) don't 1:1 match `AuditLogger`'s
generic `(action, resource, details, hash_value, prev_hash)` fields, so
those are packed into `event_data` as JSON, with `resource`'s
`isolation_id`/`policy_id` best-effort mirrored into their own columns when
a caller's `details` dict names one — no `ALTER TABLE` needed (DuckDB
0.10.0's `ALTER TABLE ADD COLUMN` has a separately-confirmed WAL-replay
crash against a persistent `.duckdb` file — see `database.py`'s
`approval_requests` comment). The bare `except: pass` was replaced with
`logger.exception(...)` so a future failure is visible.

### 4. `database.py` — sequences created after the tables that need them

Five new tables (`resonance_policy`, `resonance_actions`,
`resonance_audit_trail`, `script_library`, `script_executions`) use
`id INTEGER PRIMARY KEY DEFAULT nextval('seq_...')`. The corresponding
`CREATE SEQUENCE` statements were placed in a block *after* all five
`CREATE TABLE`s. DuckDB resolves the sequence reference at `CREATE TABLE`
bind time, not lazily at first `INSERT` — so this raised
`CatalogException: Sequence with name seq_resonance_policy does not
exist!` on the very first fresh-database `initialize_schema()` call.

**Fix:** moved sequence creation immediately before the tables that
reference it.

### 5. `core/enforcement.py` — `AuditLogger.log()` calls missing `action`

`AuditLogger.log(self, event_type, action, actor=None, resource=None,
result="success", details=None, **kwargs)` requires `action`. All seven
call sites in `AuditedHostIsolationEngine` passed `event_type` and various
`**kwargs` but never `action`, raising `TypeError: log() missing 1
required positional argument: 'action'` — the moment `self.logger`
actually became a real, working `AuditLogger` (i.e., only after fix #3;
before that, the same broken persistence meant this code path effectively
never ran for real either).

**Fix:** added an explicit `action=` to each of the seven call sites,
matching the surrounding method (`create_isolation_request` →
`"create_isolation_request"`, `simulate_isolation` →
`"simulate_isolation"`, etc.).

### 6. `core/enforcement.py` — `webhook_dispatcher.dispatch()` missing `webhook_url`

`WebhookDispatcher.dispatch(self, webhook_url, event_type, payload,
event_id=None, on_retry=None)` requires `webhook_url` as its first
positional argument. `enforce_isolation()`'s dispatch call passed only
`event_type=` and `payload=`, raising `TypeError: dispatch() missing 1
required positional argument: 'webhook_url'` on every successful
enforcement once the dispatcher was reachable. There was also no
`webhook_url` to thread through in the first place — no field on the
isolation or policy model carries one to this call site.

**Fix:** reads the same `EDR_WEBHOOK_URL` environment variable
`security_agents/edr_connector.py`'s `WebhookEnforcementConnector` already
uses (one source of truth), and skips the dispatch entirely when it's
unset rather than blocking on three retries (with exponential backoff
sleeps) against an empty URL — `_execute_isolation_action` (see #8) already
delivers the real enforcement notification through that same connector;
this is a second, best-effort ping for callers that specifically want
`WebhookDispatcher`'s envelope shape.

### 7. `core/enforcement.py` — non-deterministic isolation state reads

`_persist_isolation()`'s own docstring already said: *"This is a
placeholder; in production, add dedicated table to database.py."* It
stored `AuditedHostIsolation.model_dump()` as a JSON blob inside
`agent_logs.details`, matched back by `_fetch_isolation()` via `details
LIKE '%"<isolation_id>"%' ORDER BY timestamp DESC LIMIT 1`. Two problems,
both confirmed live: the `LIKE` substring match doesn't scope to one
isolation reliably, and — the one that actually bit a real test —
`_persist_isolation()` always inserted the object's **original**
`created_at` as the row's `timestamp`, never the current write time. Every
version of the same isolation (created → simulated → enforced → released)
therefore shared one identical `timestamp` value, so `ORDER BY timestamp
DESC LIMIT 1` had nothing to actually order by among ties — reproduced as
a `GET /resonance/enforce/{id}/status` call returning `"pending"`
immediately after a successful `enforce_isolation()` had already set the
status to `active` in a freshly-inserted row.

**Fix:** added a real, dedicated `resonance_isolations` table (`isolation_id
VARCHAR PRIMARY KEY`, `status`, `target_hostname`, `state` JSON, `created_at`,
`updated_at`) — exactly what the original TODO asked for. `_persist_isolation`
now does a real upsert (`SELECT` to check existence, then `UPDATE` or
`INSERT`, matching this codebase's established DuckDB-0.10.0-safe pattern
rather than relying on `ON CONFLICT` support); `_fetch_isolation` is a
single `SELECT ... WHERE isolation_id = ?`. Verified: exactly one row per
isolation after a full `pending → active → released` lifecycle.

### 8. `core/enforcement.py` — fabricated enforcement results

`_execute_isolation_action()`/`_execute_release_action()` returned fixed,
made-up dicts regardless of the actual target — `"affected_interfaces":
["eth0", "eth1"], "firewall_rules_added": 3` — every single time, for
every target, whether or not anything was actually enforced. The
docstrings were at least honest ("simulated in this implementation ...
In production, this would call VM, network, or EDR APIs"), which is better
than silently lying, but this branch had already built a real connector
for exactly this purpose.

**Fix:** both methods now delegate to
`security_agents/edr_connector.py`'s `enforce_containment()` /
`DockerSandboxIsolationConnector` / `WebhookEnforcementConnector` — the
same real, tested connectors `routers/response.py`'s `enforce_action`
endpoint (v2.8) already uses: a genuine Docker network disconnect via
`docker-py` if `target` names a JAKAL-owned sandbox container, or a signed
HMAC-SHA256 webhook to a configured external EDR/firewall/SOAR
(`EDR_WEBHOOK_URL`/`EDR_WEBHOOK_SECRET`) otherwise. When neither applies —
no webhook configured, target isn't a sandbox this platform owns — the
result honestly reports `"not_configured"` with an explanatory `note`,
rather than fabricating a canned success. This is the concrete
implementation of "Host isolation is a staged, audited decision — this
app has no live EDR/firewall agent to enforce it on a real network
(documented, not silently pretended)."

## What was removed

`backend/test_batch1.py` and `backend/run_tests_batch1.py` — loose,
non-pytest scripts living outside `backend/tests/`, hardcoded to
`/app/backend` (a container path that doesn't exist in this environment),
and (per the section above) exercising a `MockDB` that never touched a
real database. Replaced with `backend/tests/test_v29_batch1_reconciliation.py`,
a real pytest file that runs against actual DuckDB instances and a live
FastAPI app, targeting each of the eight bugs above plus a full
create → simulate → request-approval → enforce → status → release
lifecycle test.

`backend/jakal.duckdb` — a stale local database file left over from an
earlier round of this branch's own testing (pre-rename), carrying an old
`resonance_policy` schema that predates this reconciliation. Gitignored
(`*.duckdb`), never shipped; removed as local cleanup, not a code change.

## A second wave: "Phase 2" UI Bridge (merged after the above)

While the Batch 1 reconciliation above was in progress and being pushed,
`main` moved again with 8 more commits from what appears to be a third,
also-independent session: a new `routers/ui_bridge.py` (dashboard-shaped
REST endpoints), `frontend/js/api-client.js` and
`frontend/js/integration-loader.js` (a second frontend integration layer,
loaded in `index.html` alongside the existing `integration.js`), plus
`COMPREHENSIVE_BUILD_PLAN.md`, `HANDOFF_COMPLETE.md`, and
`PHASE_2_COMPLETION_SUMMARY.md`.

Merging this in surfaced two more real bugs, both fixed:

- **A silent, three-way path collision.** `ui_bridge.py` defined
  `GET /api/fabric/status`, `GET /api/scripts/catalog`, `GET/POST
  /api/resonance/policies`, and `GET /api/resonance/audit` — paths already
  owned by `routers/fabric.py`, `routers/scripts.py`, and
  `routers/resonance.py`, registered earlier in `app.py`. FastAPI/Starlette
  resolves overlapping exact-path routes by registration order, so these
  four `ui_bridge.py` endpoints were 100% unreachable dead code. That alone
  would just be redundant, except this branch's own `integration.js` and
  the new `frontend/js/api-client.js` both call some of these same paths
  expecting **different response shapes from different backend
  implementations** (e.g. `fabric.py`'s `/status` returns
  `security_agents`' native `FabricEngine.status()` shape; `ui_bridge.py`'s
  intended fabric endpoint returns a flattened, dashboard-specific shape).
  Reordering router registration to "fix" the dead code would have
  silently broken whichever frontend lost. Fixed by renaming the four
  colliding `ui_bridge.py` routes under a `/dashboard/` prefix (matching
  its own convention for its other 6 routes) and updating
  `frontend/js/api-client.js`'s 5 call sites to match — both frontends now
  reach their own real, distinct endpoint.
- **A live query against a nonexistent column.** `GET /api/dashboard/matrix`
  selected `findings.cvss_score`, which doesn't exist in the real
  `findings` schema (`id, pentest_id, severity, title, description,
  attack_technique, remediation, created_at` — no CVSS field) — a
  `duckdb.duckdb.BinderException` on every call, reproduced live. Fixed by
  deriving a `score` from the real `severity` column instead
  (`CRITICAL`→1.0, `HIGH`→0.75, `MEDIUM`→0.5, `LOW`→0.25).

Also normalized `ui_bridge.py`'s 10 `DuckDBManager()` direct instantiations
to the `get_db_manager()` singleton (the pattern already established
everywhere else in this codebase, avoiding redundant DB connections), and
cleaned up unused imports.

All 12 of the paths above (6 native + 4 renamed `ui_bridge.py` dashboard
routes + `/health/detailed`) verified returning `200` against a live app
instance after these fixes; full pytest suite still 112 passed, 2 skipped.
