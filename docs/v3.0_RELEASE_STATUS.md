## What's New in v3.0

### Track A: Maya-Gated Containment Hardening

**Compliance Constraints** (`security_agents/compliance_constraints.py`)
- HIPAA data residency validation (geographic boundaries)
- SOC2 availability constraint (critical service protection)
- PCI-DSS cardholder protection (CDE isolation gating)
- Pluggable constraint system for future frameworks

**Hardened Orchestrator** (`security_agents/edr_hardened.py`)
- Exponential backoff retry logic (1s → 4s → 16s)
- Transient vs permanent error classification
- Compliance pre-check before enforcement
- Error handling under network partitions
- Offline HMAC-signed token generation (15-min approval window)

**Endpoints** (new in v3.0)
- `GET /api/response/compliance/pre-check` — Real-time compliance validation
- `GET /api/response/related-targets` — Attack-path discovery (simple list)
- `GET /api/response/related-targets-v3` — Attack-path with criticality scoring

### Phase 1: Frontend Integration
- **ComplianceBadgeGroup.jsx** — Real-time compliance status display with color-coded constraint badges
- **AttackPathCanvas.jsx** — Multi-target selection UI for batch remediation
- **ResponseConsole.jsx** — Integrated console combining compliance + attack-path workflows

### Phase 2: Resilience Testing
**11 Tests** validating:
- Exponential backoff sequences (1s → 4s → 16s)
- Transient error retry (HTTP 5xx, timeouts, connection errors)
- Permanent error halt (HTTP 4xx client errors, auth failures)
- Partition simulation (webhook initially fails, succeeds on retry)
- Retry exhaustion (max_attempts threshold)
- Ontology isolation fallback (containment proceeds without ontology)
- Dead-letter queue routing for permanent failures
- HMAC token generation for offline approval

### Phase 3: Attack-Path Heuristics
**9 Tests** validating:
- Asset criticality scoring (0.0-1.0 scale):
  - Critical service flag: +0.4
  - Production status: +0.2
  - Database/Auth service: +0.15 each
  - Confidence score: +0.1x
- Multi-hop traversal (up to 4 hops for privilege escalation)
- Related targets sorted by criticality (descending) then depth (ascending)
- Supports graph sizes of 100+ nodes with <2s query time

### Phase 4: Production Polish
**7 Integration Tests** validating:
- E2E workflow: compliance → attack-path → enforcement
- Organizational priorities reflected in criticality scoring
- Deep graph traversal for 4-hop privilege escalation chains
- Compliance blocks enforcement when violations exist
- Custom retry policies work correctly
- Graph isolation prevents cross-network contamination
- Performance baseline: 100 nodes queried in <2 seconds

**API Documentation** (`docs/API_PHASE3.md`)
- Complete endpoint reference with examples
- Criticality scoring algorithm explanation
- Error handling guide (transient/permanent/compliance)
- Rate limiting and authentication requirements
- Data flow diagrams for complete workflows

## Known Limitations & Future Work

### Current Limitations
1. Criticality scoring is heuristic-based (hostname analysis, attribute flags)
   - Future: ML-based scoring from asset inventory, threat intelligence

2. Compliance constraints are framework-specific implementations
   - Future: Generic constraint language (DSL) for custom policies

3. Retry policy is global (not per-target)
   - Future: Per-target retry strategies based on asset class

4. Attack-path discovery is BFS-only
   - Future: Multi-strategy traversal (DFS, risk-weighted paths)

### Recommended Next Steps
1. **ML-Powered Scoring** — Train model on historical enforcement outcomes to improve criticality prediction
2. **Multi-Source Enrichment** — Integrate CMDB, SIEM, EDR telemetry for real-time asset context
3. **Policy DSL** — Abstract constraint language for operators to define custom compliance rules
4. **Continuous Compliance** — Monitor drift and remediate violations automatically
5. **Federated Graph** — Support multi-organization ontologies for supply-chain visibility

## Rollback Plan

If issues occur post-deployment:

1. **Immediate** — Disable new endpoints by setting RESPONSE_OK = False
2. **Short-term** — Revert to v2.8 (git checkout v2.8-stable)
3. **Medium-term** — Roll forward with hotfix branch (cherry-pick fixes onto v3.0)

### Rollback Commands
```bash
# Option 1: Disable at runtime (minimal code change)
```
